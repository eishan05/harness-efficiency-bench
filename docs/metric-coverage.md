# Metric Coverage

The benchmark reports whether each RESEARCH.md metric is supported by the traces captured in a run set.

| Metric | Current support | What is required |
|---|---|---|
| Startup tax | Full for structured per-call traces; partial for aggregate-only token usage. | Provider-first startup tax plus task-first startup tax when those are distinct calls. |
| Context growth rate | Full only when a run has at least two non-aggregate, non-preflight model calls. | Per-call `input_tokens` across turns. |
| Solve efficiency | Full when token usage is present for every run. | Success labels plus total input, output, and reasoning tokens. |

Black-box CLIs can still produce full A/B/C coverage when they expose per-call usage natively or can be routed through the local usage-only proxy. The proxy writes model name, request id, token counts, cache counts, status, and cost metadata into `.harness-usage-proxy.jsonl`; it does not store prompt or completion text by default.

Startup tax has two components when a harness emits billable provider requests that are not visible task/model turns: `provider_first_startup_tax` is the literal first billable provider request minus task prompt tokens, and `task_first_startup_tax` is the first non-preflight task/model request minus task prompt tokens. If both components refer to the same call, the call is counted once. If they refer to distinct calls, the reported startup tax is their sum.

Startup tax is unsupported for a run when the reported first-call `input_tokens` is smaller than the benchmark's rendered prompt token estimate. That usually means the harness/provider trace did not account for the full injected prompt in that request, so subtracting the prompt estimate would produce a misleading negative overhead.

Some CLIs send a small auxiliary request (for example title generation) before the first call that carries the injected agent context; Opencode and Kilo both do this. A leading call is classified as an auxiliary preflight when its input is at most 25% of the largest input among the next three calls and its overhead beyond the rendered prompt estimate is at most 2,000 tokens. Auxiliary preflight calls still count toward provider-first startup tax and solve-efficiency totals, but the task-first startup tax moves to the first non-auxiliary call and the context-growth slope excludes the auxiliary points. Affected runs record the skipped calls in `auxiliary_preflight_call_indices`. Without this rule, Opencode's reported startup tax was ~650 tokens instead of ~8.4k, and Kilo's context-growth slope was inflated by the jump from its ~1.3k auxiliary call to its ~13k first task call.

Solve efficiency is reported with both the strict denominator (oracle passed and exit code zero) and the oracle denominator (oracle passed regardless of exit code). Wall-time and budget caps make harnesses exit nonzero after a successful patch, which deflates strict counts; the oracle denominator measures task outcome alone. Token cost excludes reasoning tokens that providers report as a breakdown of completion/output tokens (`completion_tokens_details.reasoning_tokens` and equivalents), since those are already included in output tokens; only separately reported reasoning counts are additive. Traces recorded before this distinction existed keep the old additive behavior when recomputed.

Some CLIs end their native event stream with a summary event whose usage equals the cumulative totals of every prior call; Qwen Code's final `result` event does this. Such calls are detected structurally (usage matches the running input and output totals of at least two prior calls, to the token) and treated as aggregate: the docker agent parser marks them in new traces, and the metrics layer applies the same detection when recomputing from traces recorded before the marking existed. Counting Qwen's summary as a model call had doubled its solve-efficiency totals (4.36M → 2.18M tokens on the DeepSeek score-12 batch) and produced an artifactual context-growth slope of ~11.5k/turn; its true per-turn growth is ~450 tokens.

Context growth is fit on the dominant monotone conversation thread. Conversation context grows roughly monotonically within one agent thread, but some CLIs interleave a separate sub-conversation mid-run — Kilo and Opencode both drop from ~13k/7.6k input down to ~5-7k for a few calls before resuming the main thread — and a single slope across interleaved threads is biased upward by the between-thread variance. Measured calls are segmented greedily: a call continues the thread whose last input is closest below it (within a jitter tolerance of max(5%, 512 tokens) to absorb prompt trimming), otherwise it starts a new thread. The slope is fit over the largest thread using within-thread turn positions as x, and runs that segmented record `context_thread_sizes` and `excluded_call_indices` in the metric details. On the DeepSeek V4 Flash score-12 batch this moved Kilo's B median from ~1,390 to ~551 and Opencode's from ~833 to ~424 while leaving every other harness unchanged.

Context growth needs at least two non-aggregate, non-preflight model calls in the run. Claude Code Docker OpenRouter routes Anthropic-compatible OpenRouter traffic through the usage proxy; when OpenRouter returns per-request usage, that trace is sufficient for full A/B/C. Proxy requests that do not correspond to visible Claude assistant messages are retained for solve-efficiency token totals and provider-first startup tax, but ignored for context-growth calculations. Aggregate run-level usage, such as Claude Code OpenRouter `modelUsage`, is enough for solve efficiency but not enough for full startup-tax or context-growth measurement. Use `examples/tasks/metrics-calibration-multicall` when checking whether a harness can produce the B metric.

Excluded from the A/B/C comparison set:

- Antigravity CLI Docker does not currently expose token usage or a documented routeable provider base URL. It can be graded for task success, but it is not an A/B/C candidate.
- Grok Build Docker does not currently expose enough routeable or native usage telemetry for correct A/B/C measurement. It can be graded for task success, but it is not an A/B/C candidate.

The Docker OpenRouter calibration snapshot in `examples/results/openrouter-docker-smoke-calibration-2026-06-08.json` shows full startup-tax and solve-efficiency token coverage for the measurable OpenRouter harnesses. Context growth is full whenever the task produces at least two model calls; a one-call task can still report context growth as unsupported because there is no growth slope to fit.
